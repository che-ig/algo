# Суффиксное дерево vs КМП: комплексное сравнение

## 0. Главное концептуальное различие

Это сущности разных категорий, и их сравнение корректно только с оговоркой:

| | КМП (Knuth–Morris–Pratt) | Суффиксное дерево |
|---|---|---|
| **Что это** | Алгоритм однопроходного сканирования | Структура данных / индекс |
| **Что предобрабатывается** | **Шаблон** (образец поиска) | **Текст** (данные) |
| **Модель работы** | «Есть текст и needle → пробегаем текст» | «Текст проиндексирован заранее → приходим с любым needle» |
| **Аналогия** | Линейный扫描 по таблице без индекса | B-tree / полнотекстовый индекс |

Отсюда всё остальное. КМП отвечает на вопрос «как искать быстро **один раз**», суффиксное дерево — «как искать быстро **миллион раз по одним и тем же данным**».

---

## 1. Время: асимптотика

Обозначения: `n` — длина текста, `m` — длина шаблона, `k` — число вхождений, `Q` — количество запросов, `σ` — размер алфавита.

| Операция | КМП | Суффиксное дерево |
|---|---|---|
| Предобработка | **O(m)** (по шаблону) | **O(n)** (Укконен) или O(n log σ) |
| Один поиск | **O(n + m)** | **O(m + k)** |
| Q поисков | **O(Q·n + Σmᵢ)** | **O(n + Σmᵢ + Σkᵢ)** |
| Худший случай | Гарантирован, деградации нет | Гарантирован |
| Зависимость от алфавита | Нет (только сравнения) | Есть: O(m) при хеш-таблицах/массивах переходов, O(m log σ) на сбалансированных деревьях |

**Ключевой вывод:** при `Q = 1` КМП выигрывает почти всегда — суффиксное дерево надо ещё построить, а построение само по себе дороже одного сканирования. При `Q → большом` дерево выигрывает на порядки, потому что **время поиска не зависит от размера текста**.

Классический пример: геном человека (3·10⁹ символов), 10⁷ запросов. КМП ≈ 3·10¹⁶ операций (часы/дни CPU). Суффиксный индекс ≈ 10⁷·m операций (секунды/минуты).

## 2. Память

Здесь разрыв самый болезненный и именно он определяет реальную применимость.

| | КМП | Суффиксное дерево |
|---|---|---|
| Доп. память | **O(m)** — массив префикс-функции | **O(n)** узлов/рёбер, но с гигантской константой |
| В байтах | ~4·m байт (int32 на символ шаблона) | **10–20× размер текста**, при наивной реализации 30–40× |
| Нужен ли текст в RAM | Нет, можно стримить | Да, целиком + индекс |
| Пример: текст 1 ГБ, шаблон 100 симв. | **~400 байт** | **~10–25 ГБ RAM** |
| Пример: шаблон 1 МБ | ~4 МБ | не зависит от шаблона |

Причины раздутия дерева: до `2n` узлов, у каждого — указатели на детей, суффиксные ссылки, границы рёбер, parent. На 64-битных указателях это катастрофа. Плюс при 32-битных индексах текст ограничен 4 ГБ.

Для сравнения, «потомки» суффиксного дерева:

| Структура | Память на символ | Поиск |
|---|---|---|
| Суффиксное дерево | 10–20+ байт | O(m + k) |
| Суффиксный массив + LCP | 4–9 байт | O(m log n) или O(m + log n) с доп. структурами |
| **FM-index / BWT** | **0.5–2 бита** (сжатый!) | O(m) подсчёт вхождений |
| КМП | ~0 | O(n) |

FM-index занимает **меньше самого текста** — именно поэтому вся современная биоинформатика ушла на него, а не на суффиксные деревья.

## 3. Реальная производительность (константы, кэш, железо)

Асимптотика врёт про современное железо. Что происходит на практике:

**КМП:**
- Последовательный доступ к памяти → идеальная префетчинг-подружка, работает даже на стриме с диска/сети.
- Но: **не умеет «прыгать»** — ровно `n` итераций, ни одну позицию не пропускает. Зависимость по данным в переходе автомата → mispredicted branches.
- Реальная скорость: ~200–800 МБ/с на ядро.
- Boyer–Moore–Horspool в среднем делает `n/m` сравнений (пропуски) и на естественных текстах **быстрее КМП в разы**, хотя худший случай O(n·m).
- SIMD-реализации (`memmem`, `std::search` с parallel/SIMD, AVX2/AVX-512) дают **несколько ГБ/с — десятки ГБ/с**, обрабатывая 32–64 байта за инструкцию.

**Суффиксное дерево:**
- Обход = **pointer chasing**, каждый шаг — потенциальный cache miss (~100 нс). При m = 20 это может быть 20 промахов = микросекунды на запрос, что убивает теоретическое O(m).
- Построение по Укконену — тоже случайный доступ, реально ~50–300 нс/символ, т.е. **в 100–1000 раз дороже линейного сканирования**.
- NUMA/GC-давление в managed-языках (Java/C#): десятки миллионов мелких объектов — это ад для GC.

**Точка окупаемости (важно для проектирования):**

$$Q_{\text{break-even}} \approx \frac{T_{\text{build}}(n)}{T_{\text{scan}}(n)}$$

С учётом констант это **не 1–2 запроса, а десятки–сотни, а иногда тысячи** запросов к одному и тому же неизменяемому тексту. Причём если данные влезают в L2/L3 кэш, SIMD-сканирование настолько быстро, что индекс может не окупиться вообще никогда.

## 4. Функциональность: что вообще можно решить

Тут КМП и дерево не конкуренты — дерево умеет то, что КМП принципиально нет.

| Задача | КМП | Суффиксное дерево / массив |
|---|---|---|
| Найти вхождения подстроки | ✅ | ✅ |
| Подсчёт числа вхождений | O(n) | **O(m)** (счётчик в узле) |
| Наибольшая общая подстрока двух строк | ❌ | ✅ O(n₁+n₂) |
| Наибольший повтор в тексте | ❌ | ✅ |
| Наибольший палиндром | ❌ (нужен Manacher) | ✅ |
| Кол-во различных подстрок | ❌ | ✅ |
| LCP-запросы, суффиксные ссылки | ❌ | ✅ |
| Поиск с ошибкой (mismatch/wildcard) | ❌ | частично (backtracking) |
| Поиск **множества** шаблонов за проход | ❌ (нужен **Ахо–Корасик**) | ✅ |
| Работа на потоке данных | ✅ | ❌ нужен весь текст |
| Инкрементальное обновление текста | ✅ бесплатно | ❌ фактически перестройка |

## 5. Динамичность и стриминг — недооценённый критерий

- **КМП**: состояние — одно целое `j`. Можно искать в потоке логов, в Kafka-топике, в сетевом трафике, в файле на 500 ГБ, не загружая его в память. Данные изменились — ничего не инвалидируется.
- **Суффиксное дерево**: индекс жёстко привязан к конкретной версии текста. Вставка символа в середину → перестройка O(n). Есть dynamic suffix tree структуры, но константы ещё хуже. Для OLTP-данных, которые постоянно меняются, это дисквалифицирующий фактор.

## 6. Что реально используется в enterprise

Отвечу прямо: **ни КМП, ни суффиксные деревья в чистом виде в enterprise-коде почти не встречаются.** Оба — академические фундаменты, поверх которых построены практичные вещи.

### Что стоит под капотом на самом деле

| Реальная задача | Что используется в продакшене | Конкретные системы |
|---|---|---|
| `contains` / `find` в строке | SIMD `memmem`, Two-Way algorithm, Boyer–Moore–Horspool | glibc `strstr`, Rust `str::contains`, Java `String.indexOf` (JIT-интринсики + SIMD), Go `strings.Index` (Rabin-Karp + SIMD) |
| Поиск по логам, CLI | BMH / SIMD / гибрид | `grep` (Boyer-Moore + Commentz-Walter), `ripgrep` (Rust regex, Teddy SIMD) |
| Regex в приложении | NFA/DFA-автоматы, **без бэктрекинга** | RE2, Rust regex; в Java/PCRE — бэктрекинг с риском ReDoS |
| Полнотекстовый поиск по документам | **Инвертированный индекс** | Elasticsearch / OpenSearch / Lucene, Solr, Typesense, Meilisearch |
| `LIKE '%substr%'` в БД | **Триграммный / n-gram индекс** | PostgreSQL `pg_trgm` (GIN/GiST), ClickHouse `ngrambf_v1`, `tokenbf_v1` |
| WAF, IDS, антивирус, DLP (тысячи сигнатур) | **Ахо–Корасик**, Commentz-Walter, Hyperscan | Snort, Suricata, ModSecurity, ClamAV, Intel Hyperscan |
| Антифрод / матчинг правил | Ахо–Корасик, DFA | системы правил, роутеры |
| Автокомплит по префиксу | Trie / FST / radix tree | Lucene FST, Redis, поисковые саджесты |
| Fuzzy-поиск, опечатки | Levenshtein automaton, BK-tree, trigram | Lucene fuzzy, SymSpell |
| Геномика, выравнивание ридов | **FM-index / BWT, суффиксный массив** | BWA, Bowtie2, HISAT2; MUMmer (суфф. деревья/массивы), SeqAn, sdsl-lite |
| Дедупликация, поиск повторов в коде | Суффиксный массив, Rabin-Karp rolling hash | PMD CPD, jscpd, антиплагиат-системы |
| Сжатие | LZ77 + hash chains / suffix array | zstd, brotli, gzip, divsufsort |

### Почему суффиксные деревья не пошли в enterprise

1. **Память.** 10–20× от данных при том, что данные и так не влезают в RAM. Суффиксный массив/FM-index решает те же задачи в 10–100 раз компактнее.
2. **Мутабельность.** Бизнес-данные меняются постоянно, а индекс перестраивается линейно и дорого.
3. **Другой класс запросов.** Бизнесу нужен не exact substring, а **релевантность, морфология, опечатки, фасеты, права доступа, ранжирование** — это инвертированный индекс, а не суффиксный.
4. **Cache locality.** Проигрывает даже «тупому» SIMD-скану на данных до десятков МБ.
5. **Сложность реализации и поддержки.** Укконен — notoriously тонкий код; готовых промышленных библиотек мало, все нишевые (академия/биоинформатика).

### Где КМП всё-таки живёт

- Как guarantee-worst-case fallback там, где нельзя допустить ReDoS/деградации на враждебном вводе.
- В поиске по потоку, где нельзя буферизовать.
- В стриминговых парсерах, протоколах, embedded (память O(m), нетребователен).
- В преподавании и на собеседованиях — как канонический пример «префикс-функции» и амортизации.
- Как компонент внутри более сложных алгоритмов (Ахо–Корасик — это, по сути, КМП на trie; Z-функция — идейный близнец).

## 7. Практическое правило выбора

```
Один/редкий поиск по данным, которые не индексируем?
    → стандартная библиотечная find / SIMD / grep. Не пиши КМП руками.

Данные — поток / не влезают в память / постоянно меняются?
    → КМП или Ахо–Корасик (если шаблонов много), O(m) памяти.

Много фиксированных шаблонов, один проход по трафику/логу?
    → Ахо–Корасик / Hyperscan.

Текст статичен, запросов очень много,exact substring, и это ядро продукта?
    → суффиксный массив + LCP, либо FM-index. НЕ суффиксное дерево.

Нужен поиск по документам с ранжированием, языком, опечатками?
    → Elasticsearch / Lucene / pg_trgm. Не изобретай индекс.

Нужны LCS, повторы, палиндромы, кол-во различных подстрок?
    → суффиксный массив + LCP (или суффиксный автомат).
```

## Итог в одном абзаце

**КМП** — это дешёвый по памяти, кэш-дружелюбный, стриминговый алгоритм с гарантированным O(n+m), оптимален при малом числе запросов и меняющихся данных, но в продакшене почти всегда заменён SIMD-поиском или BMH. **Суффиксное дерево** — это индекс с поиском O(m+k), не зависящим от размера текста, незаменимый концептуально для миллионов запросов к статичным данным и для задач вроде LCS/повторов, но с памятью 10–20× и плохой локальностью, из-за чего в реальности вытеснено суффиксными массивами и FM-index. В enterprise же substring-поиск решается **инвертированными и триграммными индексами** (Elasticsearch, pg_trgm) для пользовательского поиска, **Ахо–Корасик/Hyperscan** для мультипаттерн-матчинга в безопасности и **библиотечным SIMD-поиском** для всего остального; суффиксные деревья остаются нишевым инструментом биоинформатики и алгоритмических задач.
